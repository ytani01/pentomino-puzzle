## きっかけ

デモのランダムの探し方が、無駄な試行錯誤を延々と続けることが多い。
`solveStepsRandom()` は、置いて解が無くなってもその場では外さない（TODO-059）。
気づくのは置ける手が尽きたときだけで、広い空きが残る盤ではなかなか尽きない。
直す前は、置いた手の 9 割以上が解の無い盤面の上だった（下の表）。

## やったこと

- `src/logic.js` の `solveStepsRandom()`: 解の無い盤面の上で置いた手
  （置いてすぐ外した手も含む）を数え、`DEMO.randomDeadLimit` に達したら、
  置ける手が尽きたときと同じく解のある盤面まで 1 手ずつ外す。
  解のある盤面か空の盤に戻ったら数を 0 に戻す（空の盤で戻さないと、
  `canContinue` が常に偽の盤では以後毎手すぐ戻る。reviewer の指摘）
- 上限で戻ったときも TODO-063 の「詰まり」に数える（`maybeCollapse()`）。
  尽きる前に気づいた行き詰まりで、数えないと崩しがほとんど起きなくなるため
- `src/config.js`: `DEMO.randomDeadLimit: 8`（利用者が決めた）とその説明
- `docs/UsersGuide.md`・`docs/developer.md`: ランダムの戻り方の説明を足した
- `tests.html`: 上限を超えないこと・超えたら ok:true まで戻ること、
  上限で戻ったのも崩しに数えること（各 8×8・6×10）を足した。
  既存の「置ける手が尽きて 1 手ずつ外す並び」の「常に偽」は、上限で浅い所から
  戻ってしまい置き済みピースの形の空きが出なくなったので、そのテストの間だけ
  上限を外した

## 確かめたこと

- `tests.html` 407 件すべて通過（tests 担当が Playwright で実行）
- 壊すと落ちる: 上限を 1000 にすると上限のテスト 2 件が、上限の分岐の
  `maybeCollapse()` を消すと崩しのテスト 2 件が落ちた
- 測り直し（Node、各盤 20 回の中央値。`archives/agents/TODO-081/measure-dead.mjs`）:

| 盤 | 置いた回数 | 解の無い盤面で置いた回数 | 続いた長さ（最長） | 最悪の回の置いた回数 |
|---|---|---|---|---|
| 8×8 | 1480 → 150 | 1400 → 97 | 127 → 8 | 4974 → 790 |
| 6×10 | 704 → 200 | 638 → 144 | 89 → 8 | 2413 → 527 |

画面での見え方（8 手で戻る動きが不自然でないか）は確かめていない。

## 分担の振り返り

- tests: 足したテストは通ったうえで、既存テスト 2 件が実装の変更で落ちることを
  見つけた（原因の見立てまで付けた）。2 回目で崩しに数えるテストを足し、
  最初の版が緩くて落ちないことを自分で見つけて書き直した
- reviewer: 空の盤で数が 0 に戻らない点と、上限で崩しに数えることを確かめる
  テストが無い点を見つけた。どちらも main は見落としていた
- measure: 数を持ち帰っただけで、見つけたことは無い
- 見込みとの食い違い: tests が 2 回になった。reviewer を tests より先に
  回していれば、テストの追加は 1 回で済んだ。料金の 36% が tests で、
  既存テストの失敗の切り分けに 1 回目の大半を使った
- 次に同じ規模なら: main が実装したら先に全件を走らせて既存テストの失敗を
  main が見てから reviewer、その指摘まで含めて tests に 1 回で頼む。
  measure は main が直す前に使ったスクリプトを走らせるだけなので、
  Haiku でも足りる
